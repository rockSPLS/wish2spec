## Итерация 0. Каркас

**Статус:** ✅ 2026-10-23 — 2026-10-25

**Цель:** рабочий каркас проекта и проверка двух главных технических рисков до того, как писать продукт: работают ли локальные эмбеддинги на Node 20 и подключается ли языковая модель по ключу.

### План

- [x] Проект Next.js 16 (TypeScript, App Router, Tailwind, ESLint), пакет `wish2spec`, порт 3003, сервер доступен только с компьютера, на котором запущен (`127.0.0.1`)
- [x] `.gitattributes`, `.gitignore` (`/.claude/`, все `.env*` кроме `.env.example`, `/data/`), файлы в CRLF, `git init` без коммита
- [x] Риск 1: локальные эмбеддинги `@huggingface/transformers` на Node 20 — скрипт `scripts/check-embeddings.mjs`
- [x] Настройки `lib/config.ts` из `.env.local`, образец `.env.example`
- [x] Риск 2: ответ языковой модели по-русски через OpenAI-совместимый сервис — маршрут проверки подключений `/api/dev/check`
- [x] Страница-заглушка
- [x] Документы: README (каркас разделов), DEV_NOTES, журнал решений
- [x] Самопроверка: типы, линтер, сборка, страница на `localhost:3003`, CRLF

### Итог

**Риск 1 — локальные эмбеддинги на Node 20: пройден.**

- Пакет `@huggingface/transformers` 4.3.1 работает на Node 20.11.1 без обходных путей (единственное — предупреждение Node `ExperimentalWarning` об импорте JSON-модулей, на работу не влияет).
- Модель — `Xenova/multilingual-e5-small` (ONNX-конверсия `intfloat/multilingual-e5-small`, лицензия MIT), квантованные веса q8, вектор из 384 чисел.
- Загрузка — около 135 МБ: `onnx/model_quantized.onnx` 118 МБ + `tokenizer.json` 17 МБ + два мелких файла настроек. Кэшируется в `data/models/Xenova/multilingual-e5-small/` (путь задан в коде; по умолчанию пакет кладёт модель внутрь `node_modules`).
- Время: первая загрузка со скачиванием — 12,5 с; повторная загрузка из кэша — 1,1 с; один эмбеддинг — 16 мс.
- Смысл различает: «напоминание о неоплаченном счёте» ↔ «уведомление о задолженности» — 0,863; с фразой «смена пароля» — 0,809 и 0,810. Порядок правильный, но разрыв небольшой — у моделей e5 близость почти всех текстов лежит в диапазоне 0,7–1,0 (так написано в описании модели), важен порядок, а не число.
- Внутри Next.js (маршрут проверки подключений) модель работает так же: те же значения близости, первый вызов 1,8 с, следующие — 14 мс. Настраивать `serverExternalPackages` не пришлось: `@huggingface/transformers` и `onnxruntime-node` уже в списке пакетов, которые Next.js 16 не собирает в бандл.

**Риск 2 — языковая модель по ключу: пройден.**

- AI SDK 6 + `@ai-sdk/openai-compatible` 2 работают на Node 20 с Vercel AI Gateway (`https://ai-gateway.vercel.sh/v1`). Проверено маршрутом проверки подключений `/api/dev/check` на модели `alibaba/qwen3.7-flash`: на вопрос по-русски — связный ответ одним предложением по-русски.
- Без настройки рассуждения модель отвечает слишком медленно для пачки пожеланий: у неё в списке AI Gateway метка `reasoning`, и рассуждение включено по умолчанию. Замеры — в «Что узнали».
- Ошибки сервиса доходят до приложения понятным текстом. На Vercel AI Gateway проверены отказ в доступе к модели и неверный ключ — ключ в текст ошибки не попадает.
- Сообщения о недостающих и неверных настройках: называются все проблемные переменные сразу, без значений (проверено без `.env.local`, с неверным адресом и с режимом `api` без модели эмбеддингов).
- В production-сборке (`npm run build` + `npm start`) маршрут проверки подключений отвечает 404.
- Запросы к маршруту с чужих сайтов отклоняются (403) по заголовку браузера `Sec-Fetch-Site`, иначе любая открытая страница могла бы тратить ключ. Проверено в браузере: адрес в адресной строке — 200 и ответ модели; переход по ссылке из терминала — 200; тот же адрес картинкой или ссылкой со страницы другого сайта — 403 с текстом «Запрос пришёл с другого сайта. Скопируйте адрес в адресную строку браузера.», запрос к модели не уходит. Программы вне браузера (curl, скрипты Node) этот заголовок не отправляют и проходят.
- Маршрут отвечает только по адресу `localhost` или `127.0.0.1` (заголовок `Host`) — защита от подмены адреса через DNS (DNS rebinding). Проверено запросами с подменённым `Host`: `localhost` и `127.0.0.1` — 200; чужой домен, даже с `Sec-Fetch-Site: same-origin`, и `localhost.evil.example` — 403 с текстом «Проверка работает только по адресу localhost или 127.0.0.1.».

**Что не работало и гипотезы:**

- `create-next-app` по умолчанию делает первый коммит — запущен с `--disable-git`, `git init` сделан вручную.
- Не ошибка, а риск из документации, учтённый заранее: при включённых Cache Components (их включает шаблон `create-next-app` для Next.js 16.4) GET-обработчик маршрута может выполниться ещё при сборке — тогда проверка вызывала бы модель во время `npm run build`. По документации добавлен `await connection()` в начале обработчика; в сборке маршрут помечен как динамический (ƒ).
- Найдено независимым ревью: по умолчанию `next dev` и `next start` слушают все сетевые интерфейсы (`0.0.0.0`) — приложение было бы видно всем в той же сети. Скрипты привязаны к `127.0.0.1` (почему так — в [журнале](docs/decisions-log.md)); проверено запуском `npm run dev` и `npm start`: по `localhost` открывается, по сетевому адресу компьютера — нет. Смена порта — `npm run dev -- -p 4000` (последний `-p` побеждает, привязка сохраняется).

**Ревью.** Независимое ревью нашло 14 замечаний, критичных нет. Исправлены привязка к `127.0.0.1`, неточности в документах, единое название маршрута проверки подключений, версия `0.0.0`, требование к Node. По решению владельца закрыт и запрос к маршруту с чужой страницы (см. выше). Оставлено одно мелкое замечание: маршрут показывает текст ошибки сервиса как есть — так видна причина отказа, а маршрут доступен только с компьютера, на котором запущен проект, и только при `npm run dev`. Понятный текст вместо сырого ответа сервиса — в v0.3. Повторные круги нашли ещё 6 мелочей в документах и затем 7 замечаний, из них одно важное — ответ 403 на ссылку с другого сайта без объяснения. Исправлены все, в том числе по решению владельца добавлена проверка `Host` от подмены адреса через DNS.

**Что узнали:**

- Абсолютное значение близости у e5 мало что говорит — порог «связей не найдено» надо подбирать на контрольном наборе (v0.2).
- Длинный текст модель обрезает до 512 токенов — это ограничивает размер фрагмента документа (учесть в v0.1 при нарезке).
- Пакет `server-only` защищает модули с ключом от случайного импорта в браузерный код.
- Скорость ответа зависит от модели сильнее, чем от кода: «рассуждающая» модель может отвечать почти минуту даже на короткий вопрос. Параметр `reasoning_effort` (в AI SDK — `providerOptions.<имя провайдера>.reasoningEffort`) AI Gateway принимает. Замер на `alibaba/qwen3.7-flash`, тот же вопрос: без параметра — 46 и 48 с, позже ещё раз 12 с (время сильно скачет); `low` — 13 с (два вызова); `none` — 1,5–2 с (три вызова); ответ по-русски связный во всех случаях. Решение — необязательная настройка `LLM_REASONING_EFFORT` (почему так — в [журнале](docs/decisions-log.md)). Какое значение ставить, `none` или `low`, проверим в v0.1 на демо-пожеланиях.

**История выбора идеи.** До кода сравнивали пять идей продукта. Для каждой — на каких данных пользователя работал бы поиск (RAG) и что делал бы AI; четыре отклонены, выбрана пятая.

1. **Подбор программы из БАД-продукции компании** по пожеланиям пользователя — с проверкой совместимости компонентов и правил приёма (время, интервалы между продуктами).
   - Данные для RAG: каталог продуктов с составами и справочник взаимодействий веществ.
   - AI: подбирает продукты под пожелание, проверяет совместимость компонентов и правила приёма, строит расписание со ссылками на составы и правила.
   - Отклонена: медицинская тематика — высокий риск советов по здоровью; справочник взаимодействий требует проверенных источников.
2. **Посты для канала сетевого консультанта.**
   - Данные для RAG: описания продукции и прошлые посты автора (его стиль).
   - AI: по ссылке на продукт и короткому описанию автора готовит пост в его стиле.
   - Отклонена: мало отличается от обычного чата с моделью — RAG здесь почти ничего не добавляет.
3. **Сказочник с памятью семьи.**
   - Данные для RAG: профиль ребёнка (возраст, любимые герои, темы, которых избегать), «мир серии» с персонажами, прошлые сказки и правки родителя.
   - AI: пишет новую сказку, которая продолжает серию и не противоречит прошлым, обыгрывает ситуацию, описанную родителем, и проверяет текст по профилю.
   - Отклонена: пока сказок мало, вся база помещается в запрос целиком, и поиск не нужен; рынок генераторов сказок занят; качество текста сильно зависит от модели.
4. **Подбор рецептов из своей коллекции.**
   - Данные для RAG: собственная коллекция рецептов (заметки, сохранённые страницы).
   - AI: приводит рецепты к единому виду, находит подходящий по тому, что есть дома, а если чего-то не хватает — адаптирует с заменами и помечает изменения относительно оригинала.
   - Отклонена: рынок приложений для рецептов плотный, боль слабее, чем у остальных идей.
5. **Ассистент заявок пользователей.**
   - Данные для RAG: документы команды (справка, прежние ТЗ, список заявок, глоссарий).
   - AI: разбирает пожелание, находит связанное, выносит вердикт с источниками, для «нового» готовит основу ТЗ.
   - Выбрана: регулярная рабочая боль, автор знает её изнутри; продукт опирается на документы команды, поэтому поиск по ним (RAG) здесь основа, а не добавка к обычному чату; у каждого вывода есть источник.

**Решения** (подробно — в [журнале](docs/decisions-log.md)): кто работает с продуктом; стек; AI SDK v6 и OpenAI-совместимый сервис; необязательная `LLM_REASONING_EFFORT`; локальные эмбеддинги с запасным режимом `api`; модель `multilingual-e5-small` q8 и кэш в `data/models/`; хранение в JSON; без деплоя; приватность; форматы; демо; порт 3003; сервер доступен только с компьютера, на котором запущен; версия `0.0.0`; защита маршрута проверки подключений от запросов с чужих сайтов; документы проекта.

### Итог

**Что сделано:**

- Демо-данные вымышленной студии йоги в `demo/`: справка по шести модулям, два прежних ТЗ, список из 18 задач, глоссарий (`.txt` без заголовков), 12 входящих заявок; ожидаемые вердикты — `demo/Ожидаемые вердикты.json`. Больше половины заявок написаны словами пользователя, а не терминами системы, две из них связаны с документами только через глоссарий («заморозить», «сгорело»), одна — в несколько строк.

- Нарезка (`lib/chunking.ts`) → эмбеддинги с префиксом `passage` → индекс `data/index.json`.
- «Входящие заявки»: загрузка `.txt` и вставка, разбиение по пустой строке или по строкам, «Найдено N» и список до добавления; заявки и результаты — в `data/requests.json`.
- Обработка (`lib/process.ts`): эмбеддинг заявки → 6 ближайших фрагментов → разбор, вердикт, обоснование и источники по строгой схеме → для «новое» второй вызов — основа ТЗ. Номера источников вне переданных фрагментов отбрасываются, затронутые модули без номеров фрагментов — тоже. Страница отправляет заявки по одной, у строки статус «В очереди», «Обрабатывается…», ярлык вердикта или «Ошибка».
- Интерфейс — одна страница: шапка, шаги 1 и 2 рядом, шаг 3 со списком (около 40 %) и карточкой; кнопки «Копировать» у основы ТЗ и у блока «Уточнить у пользователя», у основы ТЗ — ещё «Копировать вопросы»; на узком экране — один столбец, клик по строке прокручивает к карточке.
- Проверка ввода схемой zod на всех маршрутах (`lib/input.ts`), защита от запросов с чужих сайтов и по чужому адресу — на всех маршрутах (`lib/guard.ts`).
- Замеры: `npm run measure:reasoning` (маршрут замера `/api/dev/measure`, только при `npm run dev`) и `npm run measure:tokens`.

**Строгая схема ответа: работает, запасной путь не понадобился.**

- В AI SDK 6 структурированный ответ — `generateText` с `output: Output.object({ schema })`. Провайдер `@ai-sdk/openai-compatible` передаёт схему сервису (`response_format: json_schema`, strict) только с настройкой `supportsStructuredOutputs: true`; без неё уходит `json_object` без схемы, а сам AI SDK 6 схему в промпт не добавляет — модель её просто не увидела бы.
- Проверено на `alibaba/qwen3.7-flash` через Vercel AI Gateway с `none` и с `low`: ответ ровно по полям схемы, хотя в тексте пробного промпта названий полей не было. Ответ дополнительно проверяется zod, при несовпадении — один повтор.

**Нарезка и токены** (5 демо-документов):

- 45 фрагментов (до склейки коротких разделов — 50). Индексация всех пяти документов — 3,2 с вместе с загрузкой модели, повторная — 0,9 с.
- Токенизатор e5 на фрагментах из индекса: в среднем **3,72 символа на токен** (по документам 3,52–4,07, по отдельным фрагментам 3,10–4,53); 512 токенов ≈ 1900 символов — совпадает с оценкой при планировании (3,2–3,7). Фрагмент до 1200 символов даже при 3,1 символа на токен — около 390 токенов, предел 512 не достигается. Самый длинный демо-фрагмент — 258 токенов (908 символов).
- В демо нет разделов длиннее 1200 символов, поэтому деление по абзацам проверено на отдельном тексте: раздел в 1700 символов — два фрагмента, второй начинается с перекрытия от начала предложения; абзац в 2600 символов — три фрагмента по предложениям; `#` внутри блока кода заголовком не считается; разделы без текста пропускаются.

**Склейка коротких разделов.** Место нужной задачи среди всех фрагментов (в модель уходят первые 6) для шести заявок, у которых она есть в списке задач:

**Что не работало и гипотезы:**

- **№2 «похоже на задачу №3» вместо №6 (v1).** Модель взяла номер фрагмента `[3]` за номер задачи; сама задача №6 в шестёрку не попала, был только фрагмент ТЗ без номера задачи. Исправлено промптом (v2) и склейкой: вступление ТЗ «Задача №6 в списке задач» теперь в одном фрагменте с «Проблемой и целью».
- **Нужные задачи не попадали в шестёрку (v1).** Гипотеза: очень короткие фрагменты («Затронутые модули» — 42 символа, «Задача №5 в списке задач.» — 25) поиск считает близкими почти к любой заявке — они были в шестёрке у большинства заявок. Подтверждено замером (таблица выше); решение владельца — склейка коротких разделов.
- **№9 «похоже на задачу №8» (v1).** Задача №8 «Готово» и про отчёт без выгрузки; задача №14 о выгрузке в шестёрку не попала. После склейки задача №14 на 5-м месте, вердикт верный.
- **№6 «вне разработки» (v1), потом «новое».** Модель сочла продажу сертификатов не функцией программы — исправлено в v2. Но ожидается «похоже на задачу №12», а задача №12 «Подарочный абонемент» в поиске 9-я при любой нарезке: в заявке «сертификат» и «подарить», в задаче — «подарочный абонемент» и «код», пары в глоссарии нет, а модель эмбеддингов эти слова не сближает. В v0.1 оставлено как есть, без правки демо-данных; первый случай для пункта v0.2 «что модель эмбеддингов не находит». Решение владельца: в v0.2 добавить в демо-глоссарий пару «сертификат — подарочный абонемент».
- **№4 онлайн-занятия — «вне разработки» (v2).** Регресс от правки v2: в промпт добавили перечисление функций программы («продажа, оплата, запись, уведомления, отчёты»), и модель стала считать, что всё вне списка к программе не относится. В v3 перечисление заменено общим правилом границы — после этого снова «новое» при обоих значениях.
- **С `none` модель однажды «рассуждала» прямо в поле обоснования** (№2 на v2 без склейки): длинный текст с «Давайте посмотрим внимательнее», в конце которого написано «new», а в поле вердикта — similar. Больше не повторялось; если повторится — ограничивать длину обоснования в схеме.
- **Служебные имена вердиктов в тексте карточки** (нашла владелец при просмотре): «Это не out_of_scope, так как…». Модель видит английские значения из схемы ответа и пишет их в обоснование — так было у 5 из 12 заявок. Исправлено на сервере: в текстах модели служебные имена заменяются русскими ярлыками («Вне разработки»). Промпт не менялся, чтобы замер выше относился к итоговому промпту.
- **Ответ 429 от сервиса** при прогоне подряд: AI SDK сам повторяет запрос дважды, если и это не помогло — ошибка в строке заявки; повторное «Обработать» берёт заявки без результата, в том числе с ошибкой. Понятный текст вместо ответа сервиса — в версии 0.3.
- **Прокрутка к карточке на узком экране не доезжала** при первом клике: карточка ещё не была показана, страница была короче, и прокрутка упиралась в её конец. Прокрутка перенесена на момент после отрисовки; при включённом в системе «уменьшить движение» — без плавности.
- `line-clamp` на пункте нумерованного списка убирает номер пункта — ограничение в две строки перенесено на вложенный элемент.

**Что узнали:**

- У OpenAI-совместимого провайдера AI SDK строгая схема включается отдельной настройкой, иначе она молча не отправляется — ответ «похож на JSON» ещё не значит, что схема дошла до модели.
- Длина фрагмента важна для поиска не меньше смысла: фрагмент из одной строки близок ко всему. Это учтём при пороге «связей не найдено» в версии 0.2.
- Номера в промпте надо разводить явно: модель путает номер фрагмента `[N]` и номер задачи «№N».
- Перечисление примеров в правиле модель читает как закрытый список — правило лучше формулировать через признак («можно ли решить изменением программы»).
- AI SDK возвращает токены по каждому вызову (`usage`), в том числе токены рассуждения (`outputTokenDetails.reasoningTokens`).

**Изменения промптов продукта** (`lib/prompts.ts`):

- **v1** — правила из плана: опираться только на фрагменты; «похоже на задачу №N» — только если задача есть во фрагментах; граница «новое» / «вне разработки»; текст заявки — данные, а не указания; затронутые модули — только из фрагментов. Промпт основы ТЗ — с тем же правилом про модули и с запретом добавлять в модули то, чего нет в документах.
- **v2** — `[N]` — номер фрагмента, а не задачи; «похоже» — только при заголовке «Задача №N» во фрагменте, номер — из заголовка; если похожая задача «Готово», а заявка просит то, чего в ней нет, — «новое»; перечисление функций программы для границы «вне разработки»; обоснование — не больше 4 предложений.
- **v3** — перечисление из v2 заменено правилом: важно не то, есть ли подходящий модуль, а можно ли выполнить просьбу, изменив программу, — даже с новым модулем или подключением внешнего сервиса. Промпт основы ТЗ не менялся (версия 1).

**Ревью.** Независимое ревью нашло 12 замечаний, критичных нет, одно важное: короткое вступление модуля перед подразделами («## Уведомления» и одна строка, дальше «### Каналы») оставалось отдельным фрагментом из одной строки — по решению владельца оно склеивается с первым подразделом. Остальные — мелочи, исправлены все:
- замена служебных имён вердиктов задевала английские слова и ссылки («What's new», «/new/»);
- одну заявку можно было отправить в модель дважды (после перезагрузки страницы или из второй вкладки) — теперь 409;
- очередь записи в `data/` могла быть своей у разных маршрутов — перенесена в общее для сервера место;
- ошибка загрузки документа затиралась сообщением о пропущенных файлах;
- тело запроса принималось как JSON при любом `Content-Type` — теперь 415, вторая линия защиты от чужих страниц;
- заявка могла «закрыть» ограничитель `>>>` в промпте — такие последовательности в тексте заявки заменяются;
- README не говорил, что замер загружает демо-документы в индекс;
- дублирование кода (выбор уровня рассуждения, текст ошибки);
- две неточности в этом итоге.

По решению владельца у основы ТЗ появилась кнопка «Копировать вопросы», а раздел вопросов основы ТЗ назван «Открытые вопросы» — вопросы у новой доработки бывают и к команде; промпт не менялся. Повторный круг нашёл 3 мелочи: служебные имена, перечисленные через запятую или «/», заменялись не все; вступление модуля могло оказаться под заголовком короткого подраздела; три новые защиты не были записаны в журнал. Исправлены все. Третий круг замечаний не нашёл; после него на итоговом коде пройдены сборка (`npm run build`), проверка типов и линтер.

**Решения** (подробно — в [журнале](docs/decisions-log.md)): строгая схема через `json_schema` без запасного пути (запасной — в «Планах развития»); промпты в одном файле, заявка в промпте — как данные, её ограничители не подделать; склейка коротких разделов при нарезке, вступление модуля — с первым подразделом; защита от запросов с чужих сайтов и по чужому адресу на всех маршрутах, плюс только `application/json`; повторная обработка той же заявки — 409; кнопка «Копировать вопросы» у основы ТЗ; служебные имена вердиктов заменяются на сервере; рекомендованное значение `LLM_REASONING_EFFORT=none`.

**Честность замера.** Правило «результаты контрольного набора во время правок не смотрим» соблюдено не полностью: итоги исходного замера стали известны до правок кода. Но значение порога 0,79 и два признака отметки были выбраны по демо до того, как итоги исходного замера стали известны, так что на их выбор итоги контрольного набора не повлияли. Исходный прогон на демо сделан после контрольного, но на том же коде v0.1 — код между прогонами не менялся, поэтому порядок на цифры не влияет. Промпты по контрольному набору не правились, а единственная попытка правки промпта (про глоссарий) сделана и проверена на демо. Разбор №23 и его последнего абзаца после итогового замера — только просмотр, без правок кода; правки по ревью и повторный замер описаны в «Ревью».

**Что узнали:**

- У модели e5 близость зависит не только от смысла: у разных заявок «фон» близости разный, поэтому абсолютный порог годится лишь против совсем постороннего текста.
- Лучшая оценка по частям работает, когда просьба стоит в своей части; подробный рассказ в других частях может перебить её.
- Строгую схему ответа можно менять под случай: при «ничего не найдено» список вердиктов в схеме короче, и запрет держит сам сервис, а не просьба в промпте.
- pdf.js отдаёт текст кусками с признаком конца строки, иногда пустыми; абзацы приходится восстанавливать по координатам строк.
- Свежие версии `unpdf`, `pdfjs-dist` и `pdf-parse` требуют Node 20.16 или 22, а проект поддерживает Node 20, поэтому взят `unpdf` 1.7.0, и версия закреплена точно.
- В Next.js 16 обработчик маршрута не ограничивает размер тела запроса, если нет proxy, — предел нужно ставить самому.

**Изменения промптов продукта** (`lib/prompts.ts`):

- **v4** — дополнение к промпту разбора на случай, когда ни один фрагмент не прошёл порог: в документах ничего не найдено, exists и similar выбрать нельзя, в «где в системе» — «связей не найдено», без ссылок на фрагменты; в схеме ответа для этого случая — только new, out_of_scope и clarify; блок фрагментов — «в документах ничего не найдено». Итого сейчас промпт разбора — версия 4 (текст версии 3 и это дополнение), промпт основы ТЗ — версия 1.

**Ревью.** Независимое ревью нашло 20 замечаний, критичных нет. Важных два: порог 0,79, подобранный под локальную модель, действовал и в режиме `EMBEDDINGS_MODE=api`, где у другой модели эмбеддингов другой диапазон близости и порог отсёк бы всё, — по решению владельца порог теперь только в режиме `local`; DOCX склеивал слова на переносе строки (Shift+Enter), во вложенном списке и в ячейке из двух абзацев — исправлено. По решению владельца:
- номер задачи для отметки ищется во всех найденных фрагментах, а не только в процитированных, — так совпадает с утверждённым текстом причины, и отметка реже стоит зря;
- для «похоже на задачу» без номера — отметка с причиной «Номер задачи не указан — найдите её в источниках.»;
- файл, который при распаковке занимает больше 100 МБ, не разбирается: DOCX проверяется по оглавлению ZIP, PDF — распаковкой сжатых частей с пределом (тестовые «бомбы» на 214 и 330 КБ, разворачивающиеся в 200 и 300 МБ, отклонены до разбора). Лимит на размер самого файла от этого не защищает. Что не закрыто — в журнале, «Осознанно не закрыто», и в «Планах развития»;
- длинное письмо №23 — кандидат в план v0.3, если вариантов не найдётся — в «Планы развития»; абзацы PDF при большом межстрочном интервале — «Осознанно не закрыто» и «Планы развития».

Исправлены и мелочи: абзацы PDF в одну строку сливались (теперь шаг строки ограничен размером шрифта); абзац DOCX, начинавшийся с трёх тильд или трёх обратных апострофов, отключал заголовки до конца документа; ошибка внутри страницы PDF давала 500 с текстом библиотеки; предел тела запроса проверялся только по заголовку `Content-Length` (теперь тело читается частями и обрывается на пределе) и был меньше худшей допустимой загрузки (48 → 64 МБ); противоречия и неточности в журнале, README и этом итоге. Ревью отметило и два спорных ожидания контрольного набора — записаны в «Что не работало», набор не правился.

Повторный замер после правок нашёл ещё одно: модель написала «definitely out_of_scope», и имя не заменилось, потому что рядом английское слово. `out_of_scope` с подчёркиванием обычным английским не бывает — теперь оно заменяется всегда, «What's new» по-прежнему не трогается.

Второй круг ревью нашёл 4 замечания, одно важное: проверка размера PDF после распаковки считала и картинки, хотя при извлечении текста они не распаковываются, — справку со скриншотами было не загрузить (PDF на 0,6 МБ с 20 картинками, 124 МБ без сжатия). Картинки теперь пропускаются; проверено на этом файле и на обеих тестовых «бомбах». Три мелочи — в журнале, этом итоге и комментарии кода — исправлены. Третий круг замечаний к коду не нашёл, только уточнение формулировки в журнале. После него на итоговом коде пройдены проверка типов, линтер и сборка (`npm run build`). В `npm start` загружаются PDF (в том числе со скриншотами) и DOCX, скан и обе тестовые «бомбы» получают понятные сообщения, маршрут проверки подключений отвечает 404 (как и задумано: он работает только при `npm run dev`), предупреждение под шагом 2 на месте, в консоли браузера ошибок нет.

**Решения** (подробно — в [журнале](docs/decisions-log.md)): порог «связей не найдено» 0,79, абсолютный; из четырёх рассмотренных признаков отметки «Проверьте» взяты два, после ревью добавлен третий; контрольный набор в `control-set/` и замер `measure:quality`; `mammoth` и `unpdf` 1.7.0; разбор PDF и DOCX на сервере, файл — base64 в JSON; лимиты и сообщения в `lib/limits.ts`; ограничения PDF — в «Осознанно не закрыто» и «Планах развития»; после ревью — порог только в режиме `local`, номер задачи по всем найденным фрагментам, отметка для «похоже» без номера, проверка размера после распаковки DOCX и PDF.

- без документов «Обработать заново» вытесняло прежний вариант — теперь сервер отклоняет его сразу;
- правка, пока заявку изменили в другой вкладке, ложилась на другой результат — теперь 409;
- ответ 403 давал «Сервис не принял ключ», хотя сервисы отвечают им и по другим причинам — теперь общий текст;
- «Копировать вопросы» у неисправленной основы ТЗ брал вопросы из текста, а не из ответа модели;
- у «Подготовить основу ТЗ» после ошибки кнопка теперь «Повторить», как в тексте ошибки;
- не-JSON ответ сервера с кодом 500 показывался как есть;
- неточности в README, журнале и этом итоге.

Повторные круги нашли ещё: правка вердикта или основы ТЗ у заявки, которую удалили в другой вкладке, роняла страницу — теперь сервер отвечает «Заявка не найдена.»; прочие сбои загрузки документов (например, не скачалась модель эмбеддингов) показывались сырым текстом — теперь общим, а ошибка настроек в `.env.local` после этой правки скрылась за общим текстом — теперь снова показывается как есть; в терминал запуска вместе с ошибкой сервиса печаталось тело запроса — в режиме `api` при загрузке это тексты документа. Теперь туда пишутся только текст ошибки, код ответа и адрес сервиса. Так же при ответе модели не по схеме в терминал печатался весь её ответ — теперь только общий текст ошибки и причина остановки.

На итоговом коде пройдены проверка типов, линтер и сборка (`npm run build`). В `npm start` работают смена вердикта с пометкой «изменено вручную», правка основы ТЗ («Копировать вопросы» берёт исправленный текст), «Обработать заново» и «Вернуть прежний вариант», удаление заявки и всех документов с подтверждением (источники в карточках остаются), понятная ошибка «Обработать заново» без документов. Маршрут проверки подключений отвечает 404 — как и задумано: он работает только при `npm run dev`.

**Решения** (подробно — в [журнале](docs/decisions-log.md), «Инструменты аналитика»): правки хранятся рядом с ответом модели; отметка «Проверьте» снимается при ручной смене вердикта; текст заявки правится только вместе с «Обработать заново»; прежним вариантом становится только готовый результат; «Подготовить основу ТЗ» — по источникам карточки; четыре текста ошибок сервиса по коду ответа; заявку в обработке нельзя править и удалять (409); шаблоны копирования без номеров источников; после ревью — в «Копировать ответ» без источников с «Задача №N», «Что дальше» для ручного «требуется уточнение» без изменений.

Проверено на ширине 1024 и 375 px: после фильтра и после «Всего» прокрутка на месте (замечания владельца).
- Текст в 14 px читался тонким и слипшимся — теперь 15 px (замечание владельца). Неактивные кнопки показывали перечёркнутый кружок вместо курсора и не объясняли, как их включить. Сначала подсказка стала строкой рядом с кнопкой, но строка сливалась с остальным текстом шага — теперь подсказка всплывает при наведении, курсор — со знаком вопроса. В форме правки текста заявки поле оставалось доступным для ввода, пока шла обработка, а строка «Обрабатывается…» оказывалась под формой — теперь форма неактивна, строка со значком загрузки — на её кнопке. Проверено на подменённом в странице запросе, который не завершается: поле и обе кнопки неактивны; на сервер запрос не уходил.

**Что узнали:**

- Цвета через `@theme inline` становятся классами Tailwind; прежние `dark:`-классы ярлыков вердиктов после перехода на `@custom-variant` работают без изменений.
- В режиме разработки React при повторном монтировании сбрасывает атрибуты `<html>` к разметке. Переключатель ставит тему ещё раз до отрисовки (`useLayoutEffect`); после перезагрузки в тёмной теме атрибут остаётся `dark`.
- Next.js 16 сам добавляет в `<head>` ссылки на `app/icon.svg` (`sizes="any"`) и `app/apple-icon.png` (180×180).
- `lucide-react` 1.61.0 на Node 20 ставится без предупреждений, проверка типов и линтер проходят.

**Проверка в браузере** (`localhost:3003`, режим разработки, в том числе ширина 375 px): тема по настройке системы при первом заходе, переключение, запоминание после перезагрузки, без мигания (скрипт в `<head>` раньше `<body>`), переключение во второй открытой вкладке; логотип своей темы и без горизонтальной прокрутки на 375 px; новый значок вкладки. Пустые шаги — на пустых данных. «Загрузить демо-данные» загрузило 5 документов (19, 3, 3, 19 и 1 фрагмент) и 12 заявок, кнопка после этого не видна. Демо-заявки после загрузки обработаны: 12 из 12. Фильтры по всем счётчикам, пустой список с «Показать все», карточка при фильтре остаётся. Строка у «Обработать заново».

**Ревью.** Независимое ревью нашло 7 замечаний, критичных нет. Важное одно: рамка фокуса в светлой теме была цвета `#05ac7a` — 2,9:1 на белом при норме 3:1 для рамки фокуса; так же — полоса выбранной строки. Теперь у них своя переменная `--focus`: в светлой теме `#047d59`, в тёмной — прежний `#0fb883`. Исправлены и мелочи:
- после «Очистить список» фильтр и запомненная высота списка оставались, и новые заявки открывались отфильтрованными — теперь сбрасываются, когда список пустеет;
- строка «Загружено: … Нажмите «Обработать 12 заявок».» оставалась и после обработки — теперь она пропадает, когда меняется число необработанных заявок;
- ошибка «Загрузить демо-данные» советовала «Загрузите их снова» — теперь свой текст; если заявки не записались, демо-документы убираются;
- у «Загрузить файлы» во время загрузки не было подсказки «Дождитесь конца загрузки.» — теперь есть, и во время загрузки подпись выглядит как неактивная кнопка;
- неточности в журнале и в этом итоге.

Повторный круг нашёл ещё: строка «Загружено: …» пряталась, но не убиралась и появлялась снова, если после «Обработать заново» необработанных заявок опять становилось столько же, — теперь строка убирается совсем, как только число необработанных заявок меняется в первый раз; в режиме `EMBEDDINGS_MODE=api` ошибка сервиса при демо-данных советовала «загрузите документы снова» — теперь у демо-данных свои тексты с советом нажать кнопку ещё раз (тексты утвердила владелец); неточность в журнале.
